# MEP 工程材料与项目管理系统
## 全面评估与校对意见（V1.0）

> 评估对象：基于 Frappe/ERPNext 的 MEP 系统（自定义模块 + MEP 工作台 + 标准 ERPNext 模块）
> 评估日期：2026-11-07
> 评估方式：功能走查、单据链路实测、报表核对、权限与界面检查、角色场景推演
> 说明：本评估不涉及成本/价格/毛利（按业务边界暂不纳入）；历史模拟数据按"旧数据不动"处理，但会在风险中标注。

---

## 一、总体结论

**一句话：材料全链条的骨架已经搭起来，日常操作体验有明显改善；但要作为真实项目长期使用，还差"数据治理、审批内控、版本口径、移动端与培训"四块。**

| 维度 | 评分（5 分制） | 结论 |
|---|---:|---|
| 功能完整性 | 4.0 | 设计→请购→下单→到货→领用→安装主链完整，质量/文档/进口有覆盖 |
| 业务逻辑 | 3.5 | 数量联动与额度校验较强；BOM 版本、预算口径、盘点归集仍有缺口 |
| 数据一致性 | 3.0 | 主数据量大但治理不足；历史异常数据会污染报表与额度 |
| 权限与内控 | 2.5 | 角色齐全，但审批链、职责分离、审计留痕不足 |
| 界面与交互 | 4.0 | MEP 单壳、分组侧栏、专注模式、批量录入明显改善；标准表单仍偏重 |
| 易用性 | 3.5 | 批量选料/导入/台账好用；新用户学习成本、移动端、错误提示仍需优化 |
| 实用性与落地 | 3.5 | 适合作为项目材料管控主线；需试点、SOP、培训和数据清理 |
| 可实施性 | 3.5 | Docker + 备份 + 单库可落地；升级、脚本治理、环境规范需补 |
| 可维护性/扩展 | 3.0 | 自定义脚本与数据库内报表较多，需版本化与文档化 |
| 综合 | **3.5 / 5** | **可用，但未到"全项目无培训直接推广"的程度** |

## 二、业务闭环评估

### 2.1 材料主链（ strongest ）

```
设计 BOM → 请购 → 下单 → 到货 → 领用 → 安装
```

已实现：
- 按 项目×专业×系统×物料 汇总；
- 逐级数量校验（请购≤设计、下单≤请购、到货≤下单、领用≤到货/设计、安装≤领用）；
- 受控/非受控物料分流；
- 项目级三态管控（不管控/只管控受控/全管控）；
- 批量录入、Excel 导入、从 BOM 生成、按缺口生成；
- 四量台账、采购与领用台账、单据总台账、项目库存余额、物料流水。

**结论：这是系统最有价值的部分，方向正确，建议作为主线继续打磨。**

主要缺口：
1. **有效 BOM 版本口径**：目前按 `max(name)` 取"当前有效版本"，依赖单号排序，不是业务上的版本/生效日期；设计变更生成的新版是草稿，旧版不会自动失效。多版本、跨前缀（CB-/MEP-）时存在取错版本的风险。
2. **预算 vs 承诺两套口径**：Material Budget（预算）与 Material Commitment（承诺）并存，采购额度用预算、承诺台账另记，长期会出现"预算/承诺/订单"三套数对不上。
3. **盘点不归项目**：库存盘点单没有项目字段，项目库存余额/流水不包含盘点调整，项目账与仓库账可能长期差异。
4. **退料/领用退回**：已纳入物料流水，但项目库存余额的退回口径需业务确认（是否冲减领用、是否回补设计额度）。
5. **非受控物料**：不卡设计/订单链是设计选择，但"项目+专业"仍必填，现场若专业选错会污染归集。
6. **历史异常**：超设计请购、无设计领用、无项目到货等历史数据仍在库内，报表会带出；需隔离/标记/对账，不能仅靠"新单严控"。

### 2.2 质量与移交链

已有：质检单、质检模板、NCR、ITP 字段、试运行/移交、安装记录、项目文档台账。

缺口：
- 质检是否对到货形成**硬门控**（未检不能入库/领用）需确认；目前更多是记录与提示。
- NCR 整改闭环（责任、期限、复检、关闭）是否完整，需要流程验证。
- ITP 停检点/见证点、附件、电子签批未形成强约束。
- 安装记录默认草稿，未纳入正式提交/审核节奏。

### 2.3 采购与物流

已有：采购申请、采购订单、询价、供应商报价、到货入库、装运、进口案件、进口费用分摊。

缺口：
- 请购→询价→比价→下单的**审批与留痕**不足；
- 供应商交期/履约评分与订单执行未形成闭环；
- 进口/物流节点与项目材料需求的联动主要靠人工；
- 成本/价格按边界暂不做，但预算占用仍需可信。

### 2.4 项目与文档

已有：项目、专业系统矩阵、任务、项目总览、项目文档台账、里程碑齐套、实物量进度、预警。

缺口：
- 项目 WBS/里程碑与材料需求的联动较弱；
- 文档台账偏"登记"，缺版本、审批、分发、回收；
- 预警规则命中后的处理闭环（谁处理、何时关闭）需明确。

## 三、分维度详评

### 3.1 功能完整性（4.0）

优点：
- 覆盖了工程项目材料管理的主干，而不是只做进销存；
- 设计 BOM、变更、预算、承诺、采购、库存、质量、安装、移交均有落点；
- 报表体系较完整，能从"项目/专业/系统/物料/单据"多个维度看数；
- 批量录入、Excel 模板、导入预览、从 BOM 生成等便捷功能已具备。

不足：
- 缺正式的**审批流**（BOM、请购、订单、NCR、变更）；
- 缺**移动端/现场离线**能力（扫码页有，但整体未移动化）；
- 缺**成本/产值**（按边界可不做，但管理层视角会缺一块）；
- 缺**合同/供应商履约/付款**联动（若后续需要）；
- 缺**消息通知/待办**与审批集成。

### 3.2 业务逻辑与数据一致性（3.5）

做得好的：
- 数量联动是"真校验"，不是提示；提交时硬拦截；
- 受控/非受控、项目三态的设计符合"不一竿子打死"的管理诉求；
- 批量生成前清理空行、预算自动汇总等细节到位。

需要校对：
1. **BOM 有效版本**：建议增加 `is_current`（当前有效）或按 `version_no + 生效日期` 取版本；不要用 `max(name)`。
2. **预算/承诺统一**：确定唯一口径（建议以 Material Budget 为额度主账，Commitment 作为占用流水），报表只认一个口径。
3. **盘点项目化**：给库存盘点增加项目/专业/系统，或明确"盘点只对仓库账、不进项目账"，并在报表注明。
4. **退料口径**：明确退料是否回补设计额度、是否冲减领用；当前流水有正负，但额度逻辑要统一。
5. **历史数据隔离**：给测试/模拟/异常单据打标记，报表默认排除；或建立"历史对账视图"。
6. **单位换算**：采购/领用单位与库存单位不一致时的换算规则要固化，避免数量口径漂移。

### 3.3 权限与内控（2.5，最需要补）

现状：
- 角色体系较全（PM/ENG/PRC/BRA/WHS/QA/MGT/FIN/SYS 等）；
- 关键自定义单据对 All 角色做了只读收紧；
- 高级功能只对管理角色开放。

风险：
- 测试账号拥有 System Manager + 几乎所有业务角色，**职责分离形同虚设**；
- 没有 BOM/请购/订单/变更/NCR 的**审批矩阵与审批留痕**；
- 单据可被有权限的人直接修改/删除，缺关键字段变更审计；
- 没有"经办/审核/批准"三类角色字段，出问题难追责；
- 预警/异常处理没有责任人闭环。

建议：
- 建立角色矩阵：谁创建、谁审核、谁批准、谁查看；
- 关键单据启用 Workflow（至少 BOM、请购、订单、NCR、设计变更）；
- 关闭不必要的 System Manager 共享；
- 关键字段变更留痕（版本/评论/自定义审计）。

### 3.4 界面与交互（4.0）

已明显改善：
- 单一 MEP 工作台 + 高级功能抽屉，减少两个系统来回跳；
- 分组侧栏、语义图标、折叠箭头、紧凑行高；
- 深页专注模式（隐藏标准侧栏）+ 顶部返回；
- 批量选料改为分类下拉 + 分页 + 已选面板 + 导入预览；
- 顶部导航按钮（MEP/返回/前进/高级/菜单）已修复并实测。

仍需改进：
- 标准 ERPNext 表单仍偏"技术化"：字段多、英文/中文混排、术语重；
- 部分报错仍是技术语句（SQL/字段名），现场人员看不懂；
- 高级功能页 24 个卡片，首次使用仍需引导；
- 批量选料仍缺"最近使用/收藏/项目常用物料"；
- 移动端/窄屏表格、弹窗、批量操作未专项优化；
- 标准模块页与 MEP 页的视觉密度不一致。

### 3.5 易用性（3.5）

好的：
- 批量录入、粘贴、Excel 导入、模板、从 BOM 生成，大幅减少逐条录入；
- 台账筛选（项目/专业/日期/类型）贴近实际查询；
- 单据总台账一张表看全类型，减少多页面切换；
- 错误提示多数为中文业务语言。

不足：
- 新用户不知道"先建项目→再建 BOM→再请购"的顺序，需要引导；
- 部分字段（专业/系统/责任人）仍需培训；
- 没有"上一步/下一步"的表单向导；
- 没有草稿自动保存/恢复，长表单误关会丢；
- 批量导入失败行的修正需要下载再改，闭环可再顺；
- 缺角色化的首页待办（项目经理看什么、采购看什么、仓库看什么）。

### 3.6 实用性与项目落地（3.5）

适合：
- 以材料管控为主线的 EPC/机电安装项目；
- 设计 BOM 驱动请购/采购/领用；
- 项目/专业/系统三维归集；
- 质量、文档、安装、移交的过程记录。

落地前提：
- 主数据必须先治理（物料编码、单位、分类、专业系统、供应商、仓库）；
- 历史数据必须隔离/对账；
- 审批矩阵与岗位职责必须先定；
- 现场必须培训，且至少一个项目试点；
- 移动端/扫码/离线要按现场实际决定优先级。

### 3.7 可实施性（3.5）

可行：
- 单站点、单数据库、Docker 部署，备份/恢复已验证；
- 自定义模块与标准 ERPNext 共存，扩展成本可控；
- 报表可按项目/专业/类型筛选，支持导出。

风险：
- 自定义脚本、数据库内报表、Property Setter、翻译等分散，升级 Frappe/ERPNext 时需回归；
- 标准 DocType 的字段/命名规则被改过，升级可能冲突；
- 没有正式的开发/测试/生产三环境；
- 没有自动化回归测试，靠人工走查；
- 备份有，但缺定期恢复演练与升级回滚预案。

### 3.8 可维护性与扩展（3.0）

- 代码集中在 cb_erp 自定义应用，但历史一次性脚本较多；
- 报表脚本存在数据库内，版本管理弱；
- 字段/翻译/侧栏/工作区大量数据库配置，迁移需脚本化；
- 建议：把关键配置（字段、报表、侧栏、翻译）纳入版本化脚本/ fixtures，建立变更记录。

## 五、问题清单与优先级

### P0（推广前必须解决）

1. **有效 BOM 版本口径**：`max(name)` → `is_current`/版本号+生效日期；设计变更后旧版失效规则。
2. **历史异常数据隔离**：超设计请购、无设计领用、无项目到货、测试单据打标/归档，报表默认排除或单独视图。
3. **职责分离与审批**：去除测试账号的过度权限；BOM/请购/订单/变更/NCR 至少一级审批与留痕。
4. **预算/承诺统一口径**：确定唯一额度主账，避免三套数。
5. **盘点项目化或明确边界**：项目库存余额与仓库账的差异要可解释。

### P1（试点期间解决）

6. 主数据治理：物料编码/名称/单位/分类去重，停用物料标记，供应商/仓库规范。
7. 质检硬门控与 NCR 闭环：未检/不合格的收货、领用限制。
8. 移动端/扫码/离线：现场领用、到货、安装、盘点。
9. 报表性能：大表 union/无索引的查询优化，分页/物化视图。
10. 错误提示与空状态：技术错误转业务语言；导入失败可在线修正。
11. 批量录入增强：最近使用/收藏/项目常用、草稿自动保存、批量改单位/数量。
12. 文档与附件：ITP、NCR、质检报告、移交资料的附件与版本。

### P2（持续优化）

13. 高级功能页搜索/收藏/最近访问。
14. 单据总台账增加仓库/批次/序列号筛选与导出模板。
15. 角色化首页待办与 KPI。
16. 多语言（中文/葡语/英语）与本地化术语。
17. 通知/邮件/企业微信/钉钉集成（按实际）。
18. 标准模块与 MEP 的视觉/术语进一步统一。

## 六、校对与修正建议（具体）

1. **BOM 版本**：增加"当前有效"标志；设计变更提交后自动切换有效版本，旧版归档；报表/额度只认有效版本。
2. **设计变更**：新版 BOM 自动生成后进入审批，而不是长期草稿；变更影响要能追溯。
3. **预算/承诺**：Material Budget 作为额度主账，Commitment 作为占用流水；报表统一。
4. **盘点**：增加项目/专业/系统字段，或明确"盘点只调仓库账"并在项目库存报表加说明。
5. **退料**：明确是否回补设计额度；在报表与校验中统一。
6. **历史数据**：增加"数据来源/是否测试/是否异常"标记；报表默认过滤。
7. **审批**：为 BOM、请购、订单、变更、NCR 配置 Workflow；记录审批人/时间/意见。
8. **权限**：按岗位拆分账号；System Manager 只给系统管理员；关键操作双人复核。
9. **主数据**：物料编码规则、单位换算、停用/替代料、分类树治理。
10. **性能**：给常用查询字段加索引；大报表分页/缓存；避免全表 union。
11. **移动端**：现场场景优先做扫码领用/到货/安装/盘点；支持离线草稿。
12. **运维**：建立开发/测试/生产环境；配置与报表脚本版本化；定期恢复演练。

## 七、落地路线建议（90 天）

### 第 1–2 周：定规则
- 明确材料管控边界（受控/非受控、项目三态）；
- 确定审批矩阵与岗位职责；
- 确定 BOM 版本、预算/承诺、退料、盘点口径；
- 选 1 个真实项目做试点。

### 第 3–4 周：清数据
- 物料主数据去重/补单位/补分类；
- 历史异常单据打标/隔离；
- 供应商/仓库/专业系统校准；
- 建试点项目 BOM 与预算。

### 第 5–8 周：跑闭环
- 设计 BOM → 请购 → 订单 → 到货 → 领用 → 安装 全流程试跑；
- 质量/文档/移交同步；
- 每周复盘：卡点、错单、报表差异。

### 第 9–12 周：固化推广
- 修订 SOP 与表单；
- 角色培训与考核；
- 审批流上线；
- 形成推广包（模板、视频、FAQ、问题清单）。

## 八、验收指标（建议）

| 指标 | 目标 |
|---|---|
| 主数据准确率 | ≥ 98%（编码/单位/分类/项目） |
| 单据链路完整率 | ≥ 95%（无跳步、无无项目单据） |
| 超设计/超预算拦截 | 100% 硬拦截 |
| 台账与单据一致率 | ≥ 99% |
| 报表查询响应 | 常用报表 ≤ 3 秒 |
| 现场领用/到货录入时长 | 单批次 ≤ 5 分钟 |
| 用户培训覆盖率 | 100% 关键岗位 |
| 备份恢复演练 | 每季度 1 次 |

## 九、结论

这套系统的**方向是对的**：以设计 BOM 为源头，把请购、采购、到货、领用、安装串起来，再用台账和报表支撑项目管理，这比单纯进销存更贴近工程实际。

目前的状态是：**主链可用、体验改善明显，但离"全项目、全岗位、无培训直接使用"还有距离**。真正的短板不在功能数量，而在：
1. 数据治理与历史数据；
2. 审批与职责分离；
3. BOM 版本/预算口径/盘点归集；
4. 移动端与现场易用性；
5. 运维与升级规范。

建议按"**先定规则 → 再清数据 → 单项目试点 → 固化推广**"的节奏推进，不要一次性全铺开。系统本身可以承载，关键是管理和数据要先到位。
