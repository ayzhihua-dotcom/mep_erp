## 二、DocType 设计

### 2.1 主表 Design Change Request

| 字段 | 规则 |
| --- | --- |
| project / bom_list_no | 必填；定位变更对象 |
| source_version（原版本号） | 必填；Link → Design BOM（该版本须处于"已审核/锁定"态才可发起变更） |
| change_reason（变更原因） | 必填（长文本；下拉主因类别：设计修改/业主要求/技术澄清/错误更正…类目待业务确认） |
| requested_by / requested_date | 发起人（默认当前用户/日期） |
| approved_by / approved_date | 审批人（Workflow 控制回写） |
| bom_effect_version（新版本号） | 批准后由系统生成 version+1 并回填 |
| change_request_link（反向冗余） | 由 TP-PRJ-001-05 预留字段承接，双向追溯 |
| status | 状态机见第三节 |

### 2.2 子表 Change Item Line（版本差异行）

| 字段 | 规则 |
| --- | --- |
| item_code | 必填 |
| origin_qty / new_qty（原数量 / 新数量） | 必填；差额 = new − origin（展示为 diff_qty） |
| origin_required_date / new_required_date | 需求日期变更同步记录 |
| diff_action（变化类型） | 系统/人工选择：新增行 / 减量 / 增量 / 日期变更 / 取消行 |

## 三、状态机与规则

| 状态 | 转换条件 |
| --- | --- |
| 草稿 | 可编辑 |
| 已提交 | 提交即锁定主表；不得再改差异行 |
| 影响评估 | **中间态（本项目定制核心）**：系统对减量/取消行扫描下游占用（已批准 MR / 已批准 PO / 已发运 Shipment），生成《影响清单》并分派采购/项目负责人确认 |
| 已批准 | 影响评估确认完成 + 审批通过；触发生成新版本 Design BOM 草稿（调用 TP-PRJ-001-05 接口），写入 diff 行 |
| 已落地 | 新版本走完 TP-PRJ-001 状态机至"锁定"后，变更单自动标记"已落地" |
| 已取消 | 发起人或审批人可取消（留痕） |

硬规则承接 PRJ-004 /《流程规范》：

1. **不覆盖旧版本**：变化永远通过 version+1 落地。
2. 已提交的变更单主表/差异行不可直接修改，修订须取消重开。
3. 变更审批人与发起人不允许同一人（内控，对应 IC-03 同类分离）。

## 四、减量影响清单（本任务核心开发点）

### 4.1 扫描范围与数据来源

| 下游对象 | 扫描逻辑 | 产出 |
| --- | --- | --- |
| Material Request（已批准且未全额关闭） | item + 项目口径累计用量 | 该行"已转申请量" |
| Purchase Order（已批准且有效） | 经项目分配记录（PUR-007）关联 | 该行"已下单量" |
| Shipment（已发运未取消） | Shipment Item 反查 PO 行再反查需求 | 该行"已发运量" |
| 库存（可用/已领用，可选项） | 依据项目材料台账（PRJ-006 口径） | 场景：减量至低于已领用时预警 |

### 4.2 影响单据 Impact Line

| 字段 | 说明 |
| --- | --- |
| item_code / diff_qty | 对应变更差异行 |
| affected_doctype / affected_docname | MR / PO / Shipment 单号 |
| affected_qty | 建议动作数量 |
| suggested_action | 系统建议：调整 / 部分交货接受 / 退货 / 继续执行（例外处理） |
| assignee / due_date | 分派对象（采购/项目负责人）与处理期限 |
| resolution / resolved_by / resolved_date | 处理结论留痕 |

- 影响清单在"影响评估"态由定时/即时计算生成；重复计算以最新覆盖，不覆盖人工 resolution。
- 全部 impact line 无待处理项后，变更单才允许进入"已批准"（或审批人有权越过并留痕——按 D 决策，见待办）。
