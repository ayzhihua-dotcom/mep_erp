## 一、目标与恢复指标（建议值，待业务确认）

| 指标 | Dev | Test | Prod（规划） |
| --- | --- | --- | --- |
| RPO（可容忍数据丢失量） | 不做承诺（开发数据可重建） | ≤ 24 小时 | ≤ 1 小时（每日全量 + 增量/日志） |
| RTO（恢复时限） | ≤ 4 小时 | ≤ 4 小时 | ≤ 8 小时（含确认/演练路径） |
| 备份存放位置 | 本机 + 异地（Git 仓库承载配置） | 本机 + 异地副本 | 独立备份存储 + 异地副本 |

> 说明：RPO/RTO 为草案建议值，须经业务方确认冻结；冻结后写入本文件修订版，作为 S1 验收基线之一（B-01）。

## 二、备份对象与内容

| 对象 | 内容 | 方式 |
| --- | --- | --- |
| 数据库 | MariaDB 全库（site 级） | `bench backup --with-files`（或容器内同义命令 / 周期作业） |
| 附件文件 | site files 目录 | 随 `--with-files` 一并打包 |
| 配置与定制 | 定制应用源码、Custom Fields/Workflow/Print Format 等 fixtures、翻译文件（pt/en CSV） | Git 仓库提交即可，随代码即备份 |
| 环境定义 | docker-compose / bench 配置、版本核验记录 | 纳入 Git 运维目录 |
| 主数据初始化 | 主数据初始化完成后的 Dev 快照 | 手动触发 `bench backup --with-files`，保留最近 3 份 |

## 三、备份频率与保留策略

| 环境 | 频率 | 保留 |
| --- | --- | --- |
| Dev | 手动 + 关键节点（主数据初始化后、大版本升级前） | 最近 3 份 + 关键节点永久性快照（首个） |
| Test | 每日自动 + UAT 前手动 | 最近 7 份 + UAT 基线快照 |
| Prod（规划） | 每日全量 + 增量/二进制日志；也可按业务方窗口策略 | 全量按月轮换（≥ 1 个月），关键节点基线永久或按业务保留政策 |

## 四、恢复流程（标准操作，Dev/Test 适用）

1. 确认恢复目标：整体回滚（回站）/ 部分（仅数据）。
2. 准备：停止访问；如为容器，暂停应用进程但不卸载站点。
3. 执行：`bench restore <backup-sql>` + files 解压至 site files 目录。
4. 验证：站点启动、登录示例用户、抽查主数据（公司/仓库/材料各一条）与最新一张交易类单据。
5. 记录：填写《恢复演练记录》模板（第五节），归档至运维目录。

Prod 恢复流程在 O-01 决策后与本节同构细化，并增加双人操作与审批要求。

## 五、恢复演练机制（硬性要求）

| 项 | 要求 |
| --- | --- |
| 频率 | Test 环境每阶段末至少 1 次；Prod 上线前 1 次 + 每季度 1 次 |
| 演练方式 | 用最近一份备份在临时 site/实例上执行完整恢复并验收；不得只验证备份文件存在 |
| 通过标准 | RTO 内完成 + 抽查数据一致 + 示例用户可登录 |
| 记录 | 《恢复演练记录》：日期、备份文件名、耗时、结果、执行人、发现的问题 |
| 硬性规则 | 未演练通过（或无演练记录）的备份，不得视为可用备份；S1 验收第 4 条以此为准 |

## 六、Prod 补充规划（待 O-01 后细化）

- 部署形态决策（自托管/云主机/Frappe Cloud）确认后，补充：备份存储选型（对象存储/NAS）、异地副本物流（规则或工具）、加密与访问控制、备份失败告警通道（可接入 ALR 通知机制）。
- 数据保留政策（尤其是财务与进口单证相关数据的长期留存年限）由业务方/当地合规要求确认（B-02）。

## 七、验收要点（S1 第⑤交付物）

1. Dev/Test 备份作业配置完成并成功执行过至少一次（提供备份文件与执行记录）。
2. 《恢复演练记录》首份已在 Test 环境产生并达标（RTO 草案值内）。
3. 配置/定制/翻译已纳入 Git，可由仓库重建环境定义。
4. RPO/RTO 建议值经业务方确认或列入 B-01 待决。
